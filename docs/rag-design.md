# RAG 设计文档 · FastAPI 文档智能问答助手

> 面向「可信文档问答」的 RAG 设计：语料怎么洗、检索怎么配、Prompt 怎么写、引用怎么给。
> 代码：`prepare_docs.py` / `upload_docs.py`（语料） · `server.py`（代理与引用） · `index.html`（展示）

---

## 一、整体链路

```
用户提问
   │
   ▼
index.html（前端）── fetch /api/chat（同源，HttpOnly Cookie 带会话）
   │
   ▼
server.py（后端代理，Python 标准库）
   │   ① 四层防护校验  ② 注入服务端保管的 conversation_id
   ▼
Dify 对话型应用
   │   ③ 混合检索知识库（bge-m3，召回池 Top-K 20 → Rerank 精选 → 返回 Top-K 10）→ ④ LLM 生成（DeepSeek V4.1 Flash，温度 0.2）
   ▼
SSE 流式返回：answer 增量 + metadata.retriever_resources（命中片段与得分）
   │
   ▼
server.py 翻译为 meta / delta / refs / error / done 五类事件
   │
   ▼
前端：逐字渲染回答 + 右栏「引用来源」按文档聚合、画相关度得分条
```

**为什么中间要加一层自建代理**：Dify 的 API Key 只能放在服务端；同时这层代理承担了访问防护、会话隔离和事件翻译，前端不接触任何密钥与上游协议。

## 二、知识库构建

### 2.1 语料清洗（为什么不能直接喂官网 Markdown）

FastAPI 文档是给 MkDocs 构建网站用的，源码里混着大量**构建期语法**，直接导入知识库会严重污染检索结果：

| 原始形态 | 问题 | 清洗动作 |
|---|---|---|
| `{* ../../docs_src/first_steps/tutorial001_py310.py hl[1] *}` | 宏占位符，检索只能命中这行字，看不到任何代码 | 按路径读 `docs_src/**.py`，**还原成真实代码块**并推断语言 |
| 同一份代码被反复引用（每次换一组高亮行） | 展开后会重复堆积，挤占检索结果 | 同一文件**只展开一次** |
| `## 第一步 { #first-steps }` | 锚点标记污染标题 | 去掉 `{ #anchor }` |
| `/// tip \| 提示 … ///` | 提示块标记 | 压平成普通段落 |
| `<div class="termy">…</div>`（内含 span/font/u） | 控制台演示裹着 HTML | 剥离 HTML 标签，保留文本 |

产出：`docs-source/` 下 **48 篇**规范 Markdown（约 333 KB，还原 **176 个** Python 代码块），每篇开头附加一行官方原文链接（`来源：https://…`），供模型在回答里标注出处。

> 跳过 `index.md`、`dependencies/index.md`、`security/index.md` 三个纯导航页：正文少、易产生低质片段，且免费版知识库有 50 篇上限。

### 2.2 批量导入（绕开免费版限制）

Dify 免费版界面**每批只能上传 1 个文件**，48 篇手工拖入不现实 → 改用 Dataset API 的 `document/create-by-text` 批量推送（`upload_docs.py`）：

- 先 `--list` 拿 `dataset_id`，再批量推送；已存在的同名文档自动跳过（幂等）
- 接口限流约每分钟 10 次 → 每条间隔 **7 秒**，命中限流按 **60s × 次数** 递增退避，最多 6 次
- 索引失败（如 Embedding 余额不足）可 `--reindex` 用 `update-by-text` 重新触发向量化，**无需删除重传**

### 2.3 索引与分段配置

| 项 | 取值 | 说明 |
|---|---|---|
| 索引方式 | **高质量（high_quality）** | 走向量索引，不是关键词索引 |
| Embedding | 硅基流动 `BAAI/bge-m3` | 免费；多语言强，中英混排的 API 名词友好 |
| 分段 | **自动分段**（`process_rule: automatic`） | 未自定义长度，交给 Dify 按标题层级与长度自动切 |
| 检索模式 | **混合检索** | 向量语义 + 全文关键词加权，兼顾「同义改述」与「API 名精确匹配」 |
| Rerank | **`BAAI/bge-reranker-v2-m3`** | 对召回池做交叉重排，把最相关的片段提到前面 |
| 召回池 Top-K | **20**（知识库 `retrieval_model.top_k`） | 决定候选片段池大小，池越大正确片段越可能进入重排 |
| 返回 Top-K | **10**（应用「召回设置」） | 限制最终返回并交给 LLM 的片段条数 |

> 说明：Dify 里「召回条数」由两个参数共同决定，实际返回条数 = min(应用召回设置 Top-K, 知识库 `top_k`)。知识库 `top_k` 是**候选池**、应用 Top-K 是**返回上限**；两者改哪个都需各自生效（知识库走 Dataset API `PATCH /datasets/{id}` 即时生效，应用需「保存 → 发布」）。

## 三、检索策略

### 3.1 为什么是混合检索而不是纯向量

两个真实场景决定了这个选择：

- **同义改述**：「怎么限制上传文件大小」→ 文档里写的是「文件上传」「Request Files」，纯关键词匹配不到 → 需要**向量语义**。
- **API 名精确匹配**：`Depends`、`OAuth2PasswordBearer`、`CORS`、`FormData` 这类标识符，向量检索容易被泛化成「依赖」「认证」→ 需要**全文关键词**兜底。

混合检索把两路得分加权融合，正好覆盖文档问答的两类提问，比单选一种稳。

### 3.2 召回池与返回条数：为什么是「20 召回 + 10 返回 + Rerank」

一条知识点常被切成多个片段、散落在相邻 chunk 里，Rerank 又只能在「已召回的候选」里重排，因此**候选池越大，正确片段越不容易被漏掉**，再交给 Rerank 精排、取前 10 条进上下文：

- **召回池（知识库 top_k = 20）**：先把候选放宽到 20 个片段，保证正确文档大概率进入候选；否则重排模型「巧妇难为无米之炊」。
- **返回条数（应用 Top-K = 10）**：最终只把重排后的前 10 条交给 LLM，控制上下文长度与噪声。
- **Rerank（`bge-reranker-v2-m3`）**：对 20 个候选做交叉编码重排，把真正相关的片段提到 top-1，这是本版相关度提升的主要来源。

> 实测（本仓库评测）：召回池 4 → 返回 4，多个问题漏召回正确文档；召回池提到 10 → c01 命中 `first-steps.md`；提到 20 → c06 命中 `body-fields.md`（0.766，第 1 名）。最终引用命中率从 70.8% 提升到 100%。

### 3.3 引用与归属

在 Dify 应用里打开**「引用和归属（Citation & Attribution）」**，让命中的片段随回答一起通过 `metadata.retriever_resources` 返回 —— 这是前端「引用来源」面板的数据源，也是评测里客观信号的来源（见第七章）。

## 四、Prompt 设计

### 4.1 系统 Prompt 原文

```
{{#context#}}

# 角色
你是「FastAPI 文档助手」，专门基于 FastAPI 官方中文文档回答问题。

# 回答规则
1. 严格基于上方上下文（知识库检索片段）回答。上下文不足以回答时，直接说「知识库中没有找到相关内容」，
   并建议查阅 https://fastapi.tiangolo.com/zh/ ，禁止编造 API、参数或用法。
2. 用中文回答，准确、简洁；专业术语首次出现可附英文原文。
3. 涉及代码时，给出完整可运行的 Python 代码块，并简要说明关键行。
4. 回答末尾加一节「来源」，列出实际引用的文档：标题 + 链接
   （上下文中每篇文档开头有「来源：https://…」行，只用真正用到的，引用多篇就逐条列出）。
5. 与 FastAPI 无关的问题，礼貌说明你只负责 FastAPI 文档问答。
6. 用户追问时结合对话历史回答，但以上规则依然适用。
```

### 4.2 每条规则的设计意图

| 规则 | 解决的问题 |
|---|---|
| `{{#context#}}` 放**第一行** | 检索片段最靠近指令，且模型能看到「先有资料、再有要求」；漏插这个变量模型就会凭空发挥 |
| **1 防幻觉** | RAG 的底线：资料没有就明说没有，并给出权威入口，不许编造 API。对应评测里的「越界拒答率」 |
| **2 中文 + 术语附英文** | 文档是中文的、用户也是中文提问，但 API 名必须保留英文原样，否则代码跑不通 |
| **3 完整代码块** | 文档问答的高频诉求是「能直接抄的代码」，而不是片段 |
| **4 回答内自带「来源」** | 与前端的引用面板**双保险**：即使某次 API 的 `metadata` 缺失，回答正文里仍有出处 |
| **5 明确职责边界** | 让越界问题（天气、闲聊、Django）有统一、礼貌的拒答话术 |
| **6 多轮也要守规则** | 防止用户用「上一条你说过…」把模型带出资料范围 |

### 4.3 生成参数

| 参数 | 取值 | 理由 |
|---|---|---|
| 模型 | DeepSeek V4.1 Flash | 中文文档问答够用，成本低、响应快 |
| 温度 | **0.2** | 文档问答要的是「复述准确」，不是「发挥」；低温显著抑制编造 |
| 思考模式 | **关闭** | 事实型问答不需要长思考链，关掉可明显降低首字延迟 |
| 引用和归属 | **开启** | 让命中片段随 `metadata` 一起返回，供前端展示与评测 |

## 五、引用来源处理

引用来源做了**三层**，任何一层缺失都不会导致「答案没有出处」：

| 层 | 位置 | 作用 |
|---|---|---|
| ① 语料层 | 每篇文档开头一行 `来源：https://…` | 模型读得到原文链接，能在正文里写出出处 |
| ② Prompt 层 | 规则 4「回答末尾加一节『来源』」 | 回答**正文自带**出处（保底） |
| ③ 数据层 | Dify「引用和归属」→ `metadata.retriever_resources` | 结构化片段（文档名 / 段落号 / 得分），供 UI 展示 |

### 服务端：把上游结构精简后下发

`server.py` 在 `message_end` 事件里取出命中片段，**只保留前端需要的字段**再通过 `refs` 事件推送：

```python
resources = (evt.get("metadata") or {}).get("retriever_resources") or []
for r in resources:
    sources.append({
        "document_name": r.get("document_name") or "",
        "segment_position": r.get("segment_position"),
        "score": r.get("score"),
        "content": (r.get("content") or "")[:200],   # 截断，避免整段回传
    })
```

> 为什么不把整个 `metadata` 透传给前端：上游字段多且结构会变，而前端只依赖这 4 个字段；`content` 截断到 200 字可显著减小 SSE 体积。`meta / delta / refs / error / done` 这套事件名与字段构成前后端的**唯一契约**，见 `server.py` 顶部注释。

### 前端：按文档聚合 + 相关度可视化

- 收到的片段按 `document_name` **聚合**，同一篇文档下的多个段落合并展示，避免重复条目；
- 用 `score` 画**相关度得分条**（0~1），让「这条引用有多相关」一眼可见；
- `refs` 事件在 `done` 之前下发，保证回答结束时引用面板同步就绪。

## 六、访问防护与会话设计

代理层对外只暴露一个 `/api/chat`，四层防护都在服务端完成：

| 层 | 规则 | 目的 |
|---|---|---|
| 来源校验 | `Origin` / `Referer` 必须同源，缺失或不匹配一律 403 | 防止别人拿你的接口当免费 API |
| 单 IP 限流 | 每分钟 6 次 / 每天 60 次 | 防单人刷爆额度 |
| 全站上限 | 每天 500 次 | 兜底止损，保护 Dify 额度 |
| 请求体限制 | body ≤ 4096 字节，问题 ≤ 500 字 | 防大包攻击与超长输入 |

**会话隔离**：`user_id` 与 `conversation_id` 全部由服务端生成并保管，浏览器只拿到一个不透明的 `HttpOnly` Cookie（`qa_session`）。客户端传什么都不采信 —— 否则调用方可以伪造 ID 去读别人的对话。用户点「新对话」时，服务端只是把该会话的 `conversation_id` 清空，下一轮自然开启新会话。

## 七、评测发现与优化方向

用 `eval/run_eval.py` 对 28 条用例（库内 24 / 越界 4）做了全量评测，完整报告见 [eval/report.md](../eval/report.md)：

| 指标 | 结果 | 目标 | 结论 |
|---|---|---|---|
| 答案准确率 | 100%（24/24） | ≥ 85% | ✅ |
| 越界拒答率 | 100%（4/4） | 100% | ✅ |
| 引用命中率（文档级召回） | 100%（24/24） | ≥ 85% | ✅ |
| └ 严格口径（附加参考） | 95.8%（23/24） | — | 命中 且 top-1 ≥ 0.5 |
| 引用相关度（top-1 均值） | 0.86 | — | 区间 0.19–1.0 |
| 平均延迟 | 6.7s（P95 8.2s） | — | 含冷启动 |

**评测方法上的一个关键设计**：答案准确率只能用「关键词命中」做**代理指标**，但引用得分是 RAG 独有的**客观信号**。两者对照才能发现真正的问题 ——

> 早期版本把「top-1 得分 ≥ 0.5」直接并入命中率判据，结果有 5 条用例答案正确却判为未命中（top-1 只有 0.06~0.44）。复盘发现两个问题：① 判据把「召回」和「排序质量」混在一起了；② 实测库内正确召回的得分区间（0.10–1.00）与库外问题（0.00–0.24）**存在重叠**，单一门槛既切不开二者，也会把「找对了文档但排序分偏低」的正确案例误判。因此本版把二者解耦：**引用命中率**只判「文档级召回」（Hit Rate@K），**引用相关度**单列 top-1 得分，另保留「严格口径」作附加参考。

**本轮已完成的优化**：

1. **修正标注缺陷**：c08 / c16 两条用例的 `expect_docs` 标注不全，补上等价正确文档；
2. **口径解耦**：命中率（召回）与相关度（排序）分开统计，指标不再互相污染；
3. **放大召回池 + Rerank**：知识库召回池 `top_k` 由 4 提升到 20、应用返回 Top-K 设为 10，并接入 `bge-reranker-v2-m3` 重排 —— 这是命中率从 **70.8% → 100%** 的主要来源（细节见 3.2 节）。

**仍可继续的方向**：

1. **调整分段**：当前是自动分段，可改为自定义分段（按标题切、控制分片长度与重叠），让一个知识点集中在一个片段里；
2. **扩充语料**：把教程之外的 API 参考页也纳入，减少「文档里没有、模型自己答」的空间；
3. **补充评测**：加入「答案必须能在引用片段中找到依据」的判定，直接度量可溯源性。

## 八、踩坑记录

| 坑 | 现象 | 解决 |
|---|---|---|
| 硅基流动免费 Embedding 也要余额 | 48 篇全部索引失败，返回 `402 Payment Required` | 账户充值 1 元后在控制台「重试」，48 篇全部 `completed`，无需删除重传 |
| Dify service API 无法重试 `error` 文档 | `update-by-text` 报 `Document is not available` | 索引失败只能走控制台「重试」，或删除后用 `--reindex` 重传 |
| 免费版界面每批只能传 1 个文件 | 48 篇无法手工导入 | 改用 Dataset API 批量推送（`upload_docs.py`） |
| python.org 版 Python 无根证书 | 调用 Dify API 报 SSL 证书错误 | 按顺序探测系统证书路径（`/etc/ssl/cert.pem` 等）构造 SSL 上下文 |
| 越界提问仍返回引用 | 闲聊问题也带 `retriever_resources` | 看**得分**而不是「有没有引用」：越界问题的 top-1 得分普遍偏低（0.00~0.31），正常命中偏高（多在 0.5 以上），据此确定评测判据 |
| 改应用「召回设置」Top K 不生效 | 编排页 Top K 4→6→10 并发布后，API 仍固定返回 4 段 | **真正生效的是知识库自己的 `retrieval_model.top_k`**；实际返回条数 = min(应用 Top K, 知识库 `top_k`)。知识库走 Dataset API `PATCH /datasets/{id}` 改（即时生效，无需发布），应用 Top K 只是返回上限 |
